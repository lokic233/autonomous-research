## PART A — Vote on the 4 existing sibling theses

### T1: Kernel-transparent physical KV sharing
- **Vote: RED**
- **Strongest reject:** vAttention (ASPLOS'25) already delivers CUDA VMM KV with contiguous VA and unmodified kernels. The incremental delta is fork/CoW, but the repo's own data shows software baselines (vLLM-APC) are ~700× faster on fork latency and ~6× larger capacity at 32-block prefix. The "win" evaporates under the baseline that matters.
- **Fatal baseline:** vAttention for the contiguous-VA claim; vLLM PagedAttention for the practical sharing claim.
- **Rationale:** Repo's own WRITEUP concedes: against strong software baselines, this is not a practical capacity/speedup win. The architectural novelty over vAttention is thin — both use cuMemMap for contiguous VA; adding CoW doesn't constitute a paper-level contribution when the CoW path is slower than software refcounting by three orders of magnitude.

### T2: VMM mapping-ceiling K≈520K characterization
- **Vote: YELLOW (leaning RED)**
- **Strongest reject:** "This is a measurement, not a mechanism." A single empirical constant (520K) with one root-cause finding (driver-internal cuMemSetAccess, not Linux VMA) is a strong section of a paper, not a paper itself.
- **Fatal baseline:** Any future NVIDIA driver update could change this constant, making the characterization a snapshot rather than a law.
- **Rationale:** Data is solid (Metric 4/4b, ±1% across {1,3,6,12}GiB, Lab 1 confirming 392 VMAs vs 67M limit). But the community impact requires showing this ceiling bites a real system. vAttention's paper does not report hitting this wall, so the relevance is speculative until someone deploys VMM-KV at scale and OOMs at cuMemSetAccess.

### T3: EDMM speculative prefill
- **Vote: YELLOW**
- **Strongest reject:** B4 recovery is an oracle upper bound. The claim "recovery C/A=1.17×" assumes the runtime can perfectly predict the contaminated prompt token sequence during the tool-call idle window. Real speculation hit-rate is unproven. V1 fork deadlocks on multi-tenant H100. The gap between "oracle says 1.17×" and "production system achieves X" could be arbitrarily large.
- **Fatal baseline:** Continuum / LMCache are closing the speculative-prefill / KV-offload window month by month. If they solve tool-call contamination with a software-only radix-tree patch, the VMM mechanism becomes unnecessary.
- **Rationale:** The PROBLEM measurement is strong (P1.3: superlinear TTFT penalty, 1.38×→5.41× in vLLM, 1.61×→5.24× in SGLang). The SOLUTION is unvalidated beyond oracle. Paper-grade only if the oracle gap is closed with a realistic prediction model.

### T4: Counterfactual replay for failure attribution
- **Vote: RED**
- **Strongest reject:** No implementation, no empirical validation, no measured system. Repo 3 is a committee framework and transcripts. The "counterfactual replay" concept has zero measured data — no trace store exists, no replay was executed, no attribution was computed.
- **Fatal baseline:** Standard distributed tracing (OpenTelemetry + span-level attribution) already provides failure attribution for multi-step workflows without requiring KV-level replay.
- **Rationale:** "Unbuilt" is not recoverable in 30 days given the scope (trace store + replay engine + attribution logic + evaluation on real agent failures). Committee deliberation is not evidence.

## PART B — Propose NEW thesis candidates

### NEW-T5: Prefix-Cache Fragility Under Multi-Turn Injection: A Workload Characterization for Agentic Serving

- **Repo / evidence basis:** edmm P1.3 (vLLM 1.38×→5.41× 4K→32K; SGLang 1.61×→5.24×), P0.1/0.2 (28-layer KV verification). Measured on two independent serving engines with live engine integration.
- **Contribution type:** workload model / characterization
- **Closest prior work + why this is outside it:** RadixAttention (NeurIPS'24) and PagedAttention (SOSP'23) characterize prefix-sharing benefits but do NOT model the contamination case where tool-call responses break hash chains. No published work measures TTFT penalty from mid-prompt injection across engines, let alone shows superlinear scaling.
- **Closest OSS competitor + why it does not invalidate:** vLLM/SGLang both EXHIBIT the problem; neither characterizes it. This is measuring a failure mode of existing systems, not competing with them.
- **Anti-FlashInfer test:** YES — FlashInfer speed is irrelevant; the cost is KV recomputation caused by hash-chain breakage, not kernel execution time. Even infinitely-fast FlashInfer must recompute all post-contamination KV blocks.
- **No-Code test:** "Multi-turn agentic prompts cause superlinear TTFT degradation in prefix-caching serving systems because tool-call responses inject unpredictable tokens that break hash-chain prefix matching, forcing full KV recomputation that scales with context length." This knowledge stands.
- **Baseline-death test:** If vLLM or SGLang ships a "dirty-block" incremental hash update that tolerates mid-sequence injection without full recompute, the penalty measurement becomes historical. Check vLLM issue tracker for this.
- **Highest-EV experiment:** Hypothesis: TTFT penalty is superlinear in context length AND sublinear in tool-response length (i.e., even short injections cause disproportionate damage). Cost: 2 GPU-days on H100, sweep context lengths 2K–64K × injection lengths 32–2048. Min success: confirm superlinear context scaling AND publish the first analytical model (predicted vs measured penalty). Kills: any claim that prefix-caching "handles" agentic workloads.
- **30-day test:** YES — measurement infrastructure already exists in edmm repo. Need to broaden the sweep, add Llama models, write the analytical model, and package.
- **Venue:** MLSys (workload characterization) or ATC/EuroSys (systems measurement)
- **MY VOTE: GREEN** — The data exists, the finding is novel (no published prefix-cache contamination model), and the contribution is solution-independent.

### NEW-T6: CoW Event Counting as a Zero-Overhead Divergence Oracle for Branching Inference

- **Repo / evidence basis:** forkedkv Metric 5b (448 CoW events in real Qwen2.5-7B decode, bit-identical output), Metric 5c (tree-of-thought rollback fires CoW exactly once, copies exactly 1 page, siblings uncorrupted).
- **Contribution type:** systems mechanism / runtime primitive
- **Closest prior work + why this is outside it:** vAttention does VMM KV but has no fork/CoW → no CoW events to count. Speculative decoding tracks token acceptance rates but at the generation level, not at the physical-memory divergence level. No prior work uses page-level CoW event counts as a branch divergence metric.
- **Closest OSS competitor + why it does not invalidate:** vLLM's block manager tracks logical block refcounts but does not know WHICH blocks diverged or WHEN — it's a capacity accounting tool, not a divergence profiler. CoW event counting gives temporal, per-page divergence information.
- **Anti-FlashInfer test:** YES — this is about memory-state observability, not kernel speed. FlashInfer doesn't observe or report which KV pages were written.
- **No-Code test:** "In a CoW-forked KV system, the count and location of copy-on-write events provides an exact, zero-query-overhead measure of how much a branch has diverged from its parent, enabling divergence-aware scheduling and pruning in tree search." The insight stands.
- **Baseline-death test:** If someone builds a pure-software divergence counter at the PagedAttention block level that's equally precise and lower cost, the VMM-based approach loses its advantage. Software block-level dirty-bit tracking is straightforward to implement.
- **Highest-EV experiment:** Hypothesis: CoW-event-aware pruning in tree-of-thought reduces exploration cost by ≥20% vs uniform pruning (prune branches with highest divergence-per-token first). Cost: 3 GPU-days, implement CoW event callback + pruning policy on existing forkedkv infrastructure, run on 50 GSM8K problems. Min success: ≥15% fewer total generated tokens at iso-accuracy. Kills: the "CoW is just an implementation detail" dismissal.
- **30-day test:** MAYBE — the primitive exists (Metric 5c), but building a tree-search system on top and showing the divergence oracle improves search quality is tight for 30 days.
- **Venue:** Workshop (if measurement-only) | MLSys (if divergence-aware scheduling shows gains)
- **MY VOTE: YELLOW** — The primitive is real and measured, but the value proposition requires showing it improves downstream search quality, which is undemonstrated.

### NEW-T7: Tool-Call Idle-Window Scheduling as a First-Class Serving Primitive

- **Repo / evidence basis:** edmm measures tool-call latency window (274ms recompute vs 58µs swap), P1.3 shows the penalty that idle-window scheduling avoids. The scheduling insight: tool-call execution creates a predictable idle window on the GPU where speculative KV precomputation can run without contending with decode.
- **Contribution type:** runtime primitive / optimization
- **Closest prior work + why this is outside it:** Orca (OSDI'22) does iteration-level scheduling; Sarathi-Serve (OSDI'24) does chunked-prefill scheduling. Neither models tool-call idle windows as a scheduling resource. No serving system treats "GPU is idle while waiting for tool response" as a first-class scheduling event.
- **Closest OSS competitor + why it does not invalidate:** vLLM/SGLang both treat tool-call waits as request-level pauses; the GPU serves other requests. This thesis says: use that idle window FOR THE SAME REQUEST's speculative KV work, not just for other requests.
- **Anti-FlashInfer test:** YES — the scheduling primitive is about WHEN to compute, not HOW FAST to compute. FlashInfer speed doesn't help if you're computing the wrong KV (or recomputing KV you could have speculatively prepared).
- **No-Code test:** "Agentic serving workloads contain predictable GPU idle windows during tool-call execution; a serving scheduler that uses these windows for speculative KV precomputation can eliminate the radix-contamination TTFT penalty." This is a scheduling insight.
- **Baseline-death test:** If vLLM's scheduler already preempts and reschedules requests efficiently enough that tool-call idle windows are fully utilized by OTHER requests, the opportunity cost of dedicating them to speculative prefill may be negative under high load.
- **Highest-EV experiment:** Hypothesis: Under mixed agentic+non-agentic load, idle-window scheduling for speculative KV achieves ≥50% of oracle recovery (C/A ≤ 1.6× vs oracle 1.17×) with ≤5% throughput impact on co-located non-agentic requests. Cost: 5 GPU-days, implement idle-window callback in vLLM scheduler. Min success: ≥40% of oracle at ≤10% throughput cost. Kills: the "just serve other requests during tool calls" dismissal.
- **30-day test:** MAYBE — requires vLLM scheduler integration (edmm's V1 fork deadlocked on IPC). The scheduling concept is clean but vLLM internals are gnarly.
- **Venue:** MLSys | OSDI/SOSP (if full scheduler integration demonstrated)
- **MY VOTE: YELLOW** — Clean insight, but the implementation gap (edmm's V1 deadlocked) is a concrete risk. Also vulnerable to "the scheduler should just serve other requests" attack.

### NEW-T8: Design-Space Decomposition of GPU Copy-on-Write Mechanisms

- **Repo / evidence basis:** forkedkv measured three distinct CoW mechanisms with quantified tradeoffs:
  - Page-remap CoW: 178µs/page, preserves contiguous VA, 13µs is D2D copy (7%), 165µs is mapping overhead
  - VA-swap CoW: 59% faster than remap, breaks contiguous VA (data/metric shows this)
  - Software refcount (vLLM-APC): ~700× faster fork latency, ~6× larger capacity at 32-block prefix, requires PagedAttention
  - B8 scratch-pool: only 3% faster (R1's "47% removable" retracted)
- **Contribution type:** characterization / systems mechanism
- **Closest prior work + why this is outside it:** vAttention characterizes VMM allocation but does not implement or measure CoW. No published work decomposes GPU CoW latency or compares hardware-vs-software-vs-hybrid mechanisms with measured data.
- **Closest OSS competitor + why it does not invalidate:** vLLM's block-copy is one data point in this design space. This thesis maps the full space.
- **Anti-FlashInfer test:** YES — CoW mechanism choice determines memory management overhead, orthogonal to kernel speed.
- **No-Code test:** "GPU copy-on-write admits at least three distinct mechanism families (page-remap, VA-swap, software-refcount) with fundamentally different tradeoff profiles: remap preserves contiguous VA at 178µs/page; VA-swap is 59% faster but breaks VA contiguity; software is 700× faster but mandates paged kernels. The 165µs non-copy overhead in remap is mapping metadata, not data movement." This taxonomy and latency decomposition survives.
- **Baseline-death test:** If NVIDIA exposes a first-party CoW API in a future CUDA release, the characterization becomes a historical curiosity. Also, if the 165µs mapping overhead is a fixable driver bug rather than fundamental, the decomposition's conclusions shift.
- **Highest-EV experiment:** Hypothesis: the 165µs mapping overhead scales with number of existing mappings (i.e., cuMemSetAccess cost is O(existing_mappings)). Cost: 1 GPU-day, sweep mapping count 1K→500K and measure per-page remap latency. Min success: confirm or refute linear scaling. Kills: if confirmed, this connects the CoW latency decomposition to the K≈520K ceiling (T2), creating a unified story.
- **30-day test:** YES — all measurements already exist in the repo. Need to add the scaling sweep, formalize the design-space taxonomy, and write up. This is a measurement/characterization paper.
- **Venue:** ATC/EuroSys (systems characterization) | ASPLOS (if tied to architectural implications)
- **MY VOTE: YELLOW** — Real data, clear taxonomy, but "design space survey of a mechanism nobody uses in production" is a hard sell. Needs the "when should you use which" prescriptive angle to reach GREEN.

### NEW-T9: Superlinear Recomputation Scaling as a Fundamental Limit of Hash-Based Prefix Caching

- **Repo / evidence basis:** edmm P1.3: vLLM penalty scales 1.38×(4K)→5.41×(32K); SGLang 1.61×(4K)→5.24×(32K). The superlinearity (not just linear in context length) is the key finding — it implies hash-based prefix caching degrades FASTER than the context grows.
- **Contribution type:** workload model / characterization (analytical)
- **Closest prior work + why this is outside it:** PagedAttention (SOSP'23) analyzes prefix-sharing benefits analytically; no published work analyzes the FAILURE MODE analytically. Radix tree analyses assume monotonic prefix extension; none model mid-sequence contamination.
- **Closest OSS competitor + why it does not invalidate:** This explains WHY vLLM and SGLang degrade — it's a theoretical result about a class of algorithms, not a competing system.
- **Anti-FlashInfer test:** YES — superlinearity arises from hash-chain propagation, not from kernel speed. Even with infinitely-fast recomputation kernels, the NUMBER of blocks requiring recomputation grows superlinearly.
- **No-Code test:** "Hash-based prefix caching exhibits superlinear TTFT degradation under mid-sequence token injection because a single contaminated block invalidates all downstream hash-chain entries, and the number of downstream blocks grows with context length while recomputation cost per block also grows (attention over longer prefixes)." This is a theoretical insight.
- **Baseline-death test:** If someone proposes a hash function that tolerates mid-sequence mutation (e.g., block-local hashing with position-independent keys), the superlinearity disappears. The question is whether such a hash function can maintain correctness guarantees.
- **Highest-EV experiment:** Hypothesis: the superlinear exponent is ≈1.3–1.5 (i.e., TTFT ∝ L^α where α>1, L=context length) and is predictable from the attention cost model. Cost: 2 GPU-days, fit the analytical model to measured data across 2K–64K contexts. Min success: R²≥0.95 on the power-law fit. Kills: the assumption that prefix-caching overhead is "just linear recomputation."
- **30-day test:** YES — data exists in edmm, need to broaden the sweep and derive the analytical model.
- **Venue:** MLSys | NeurIPS (if the analytical model is tight and general)
- **MY VOTE: YELLOW** — The superlinearity observation is genuinely new, but it could end up being a straightforward consequence of quadratic attention cost rather than a deep structural insight. If the explanation is just "recomputing K blocks of attention where each block sees a longer prefix = O(K²)" then the contribution is thin.

## PART C — Top 3 NEW theses ranked

1. **NEW-T5 (Prefix-Cache Fragility Characterization)** — strongest because the problem measurement is complete, novel, solution-independent, and reproducible. Two-engine validation eliminates the "vLLM-specific artifact" attack. Can merge with NEW-T9's analytical model for a stronger paper.

2. **NEW-T8 (GPU CoW Design-Space Decomposition)** — the latency decomposition (178µs total, 13µs data copy, 165µs mapping overhead) and three-mechanism comparison are unique measurements nobody else has published. Weakened by "who cares if nobody uses GPU CoW in production?"

3. **NEW-T9 (Superlinear Recomputation Scaling)** — complements T5 with an analytical model. Could be merged into T5 or stand alone if the power-law exponent is structurally interesting rather than trivially explained by quadratic attention.

**Which I'd defend as GREEN:** Only **NEW-T5**, and only if executed as a combined problem-characterization + analytical-model paper (merging T5 and T9). The problem is real, measured across two production engines, affects every prefix-caching serving system under agentic workloads, and no published work characterizes it. The solution space (EDMM, dirty-block hashing, incremental radix update) is explicitly scoped out — this is a "here's a problem the community hasn't measured" paper, which is the hardest kind to kill because the data speaks for itself.

I would NOT defend T6, T7, T8, or T9 as standalone GREEN. T6 and T7 have thin value propositions without downstream impact evidence. T8 characterizes a mechanism space with no production users. T9 risks being "quadratic attention causes quadratic recomputation, obviously."
