## 1. Audit of the §G6 AMD-transfer argument (the gating check)

**The argument (gapmine-r3 §G6):** SW prefix-share fork = O(1) pointer refcount, ZERO mapping syscalls.
AMD VMM-CoW fork must pay ≥1 `hipMemMap`+`hipMemSetAccess` per diverged page. AMD's finer 4 KiB granule
(vs NVIDIA 2 MiB) *relaxes capacity* (CLAIM-0002: no wall to 80M) but *tightens per-op cost* (512× more
per-page map syscalls per byte of branch divergence). Since CLAIM-0001 already establishes the **per-op
fork tax — not capacity — as the binding reason HW loses**, AMD makes the binding loser STRICTLY WORSE.
∴ the 0/12 SW-win transfers to AMD by construction.

**Soundness check — does each premise hold against the promoted evidence?**

| Premise | Source | Holds? |
|---|---|---|
| P1: SW fork = O(1), 0 mapping syscalls | DEAD-0001 (SW refcount, 240× faster at fork); CLAIM-0001 SW arm | ✅ measured |
| P2: per-op fork tax (not capacity) is the binding loser on NVIDIA below the ceiling | CLAIM-0001: 0/12, 1.06–2.20× slower than SW *even below the ceiling* (the 12-cell grid is sub-ceiling) | ✅ this is exactly what 0/12 means — HW loses on cost where capacity is NOT the constraint |
| P3: AMD VMM-CoW pays ≥1 map syscall per diverged page | CUDA/HIP VMM API semantics (cuMemMap/hipMemMap per granule) — accounting identity, no probe needed | ✅ definitional |
| P4: AMD 4 KiB granule = 512× more map ops per byte of divergence than NVIDIA 2 MiB | 2MiB/4KiB=512 (CROSSVENDOR_RESULT verified) | ✅ arithmetic |

**The hostile-reviewer attack I tested: "Could AMD's relaxed capacity ceiling FLIP a cell that NVIDIA lost
only because of the ceiling?"** — i.e. is any of the 0/12 NVIDIA losses caused by capacity rather than
per-op cost? If so, removing the ceiling on AMD could in principle flip it.

**Answer: NO, and this is the crux that makes G6 airtight.** The 0/12 grid (EXP-A001, `ec_rollback_e2e.csv`,
prefix{4096,512}×N{4,16}×R{0,4,16}) is a SUB-CEILING per-op latency grid — the ceiling crash is a SEPARATE
phenomenon measured in EXP-A003 (CLAIM-0003) at B≥128. So none of the 12 cells lost *because of* capacity;
all 12 lost on per-op cost while capacity was non-binding. The ceiling and the per-op tax are evidentially
DISJOINT (the camera-ready even splits crash classes: ceiling_crash vs transient). Therefore relaxing the
ceiling on AMD touches a variable that was NOT the cause of any of the 12 losses. AMD changes exactly two
things vs NVIDIA: (a) capacity ↑ (was never binding in the grid → cannot flip a cell), (b) per-op map count
↑512× (was the binding loser → makes SW's O(1) win WIDER). Both deltas push the same direction: SW wins by
more, never less. **There is no regime where AMD flips a sub-ceiling cell.** The argument is closed.

**One honesty caveat (does not change APPLY):** G6 is correct *for branch divergence that materializes as
new physical pages requiring map calls* — i.e. the agentic fork-then-write workload the whole project is
scoped to. It is NOT a universal "AMD VMM is always worse" claim; it is scoped to the per-op fork tax on
divergence, which is precisely CLAIM-0001's scope. The proposed map-delta should be worded as
"per-op fork-cost axis transfers to AMD" — NOT "AMD VMM is dominated in general." gapmine-r3's own wording
("indictment is not NVIDIA-specific on the *per-op cost* axis; only the *capacity ceiling* is
NVIDIA-specific") already respects this scope. ✅ Apply as worded.

**Status:** AMD-transfer argument **VERIFIED SOUND**. It is an accounting identity over already-GREEN

### 2.1 The one tension a hostile reviewer WOULD probe — RESOLVED, not a contradiction
CLAIM-0007 says SW "cannot express" bit-identical write-after-share. DEAD-0001 (and gapmine G3) says SW
"matches HW isolation bit-for-bit." **These are different properties and do not contradict:**
- **DEAD-0001 / G3** = the *VALUE* property: SW refcounted snapshot yields the same bit-identical KV bytes
  and the same branch isolation (no cross-branch corruption). True, and it kills the *isolation-as-safety*
  and *replay-determinism* claims.
- **CLAIM-0007** = the *MECHANISM* property: the GPU MMU diverges a shared page lazily on first write,
  **kernel-transparent** (`kernel_modified:false`, attention reads the post-CoW page with no code change,
  max_abs_diff=0.0 vs full clone). SW prefix-sharing achieves the same bytes via an *explicit copy /
  separate buffer + pointer swap* (the application/runtime manages divergence), NOT via transparent MMU CoW.

So "SW cannot express" is precise: SW cannot express *transparent MMU-level CoW* — it must copy explicitly.
It CAN express the same end-state bytes and isolation. The camera-ready handles this exactly right: CLAIM-0007
is framed as the "sole HW advantage … orthogonal to performance … does not redeem the abstraction" — i.e. a
mechanism nicety with no performance payoff, NOT a load-bearing win. **No over-claim, no inconsistency.** A
reviewer who conflates them is answered by the §6 concession framing. ✅
